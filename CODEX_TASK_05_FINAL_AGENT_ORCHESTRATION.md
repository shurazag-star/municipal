## Контекст

Проект `Municipal` уже имеет хороший технический фундамент: Rails-приложение, рабочее место агента, загрузку файлов, парсинг DOCX/XLSX/PDF, OCR fallback для PDF-соглашений, построение дерева муниципальной программы, ChangeSet, DOCX patch/export, post-export validation, LibreOffice render-check, OpenRouter-модели и базовый чат.

Но текущая версия все еще не дотягивает до целевого клиентского сценария:

> Пользователь загружает порядок разработки, текущую муниципальную программу и документы-основания изменений. Далее он общается с агентом обычным языком. Агент сам понимает, каких документов не хватает, запускает нужные инструменты, показывает расхождения, объясняет изменения, просит подтверждения спорных строк, формирует новую редакцию DOCX и отчет, перепроверяет результат и дает ссылки на готовые файлы прямо в чате.

Важно: LLM не должна считать деньги сама. Но агент обязан уметь считать через инструменты, проверять через инструменты, объяснять результат человеческим языком и вести пользователя до результата.

## Главная цель итерации

Сделать чат не просто маршрутизатором одной команды, а полноценным рабочим агентом с инструментами и безопасным пошаговым сценарием.

Итоговый пользовательский сценарий должен работать так:

1. Пользователь пишет: «проанализируй документы».
2. Агент проверяет наличие порядка, DOCX-программы и документов-оснований.
3. Если чего-то не хватает — агент прямо в чате объясняет, что нужно загрузить.
4. Если все есть — агент запускает анализ, формирует проект изменений и показывает понятную сводку.
5. Пользователь пишет: «где несовпадения?» — агент показывает строки/годы/объекты с расхождениями и причины.
6. Пользователь пишет: «что поменялось по Черустям?» — агент показывает объект, год, источник, было/стало/разница, основание.
7. Пользователь пишет: «покажи спорные строки» — агент показывает спорные строки с кнопками/действиями подтверждения.
8. Пользователь пишет: «подтверди надежные строки» или «подтверди проект» — агент корректно подтверждает только допустимые строки/проект.
9. Пользователь пишет: «сформируй новую редакцию» — агент применяет подтвержденный проект, формирует DOCX/отчет, запускает самопроверки.
10. Если проверки пройдены — агент дает карточки скачивания DOCX и отчета в чате.
11. Если проверки не пройдены — агент не выдает документ как финальный, а объясняет проблему.

## Что сейчас надо исправить

### 1. Добавить настоящий workflow-слой агента

Сейчас `AgentOrchestrator` выполняет один intent за одно сообщение. Этого мало для живого сценария.

Добавить сервис:

```ruby
AgentWorkflowRunner
```

Он должен:

- принимать `user_message`, `conversation`, `context`;
- определять намерение через `AgentIntentRouter`;
- выбирать один или несколько шагов;
- выполнять инструменты через `AgentToolRegistry`;
- обновлять контекст после каждого важного шага;
- формировать итоговый ответ через `AgentResponseComposer` / `AgentAnswerGenerator`;
- иметь безопасный лимит шагов, например `max_steps: 5`;
- никогда не применять DOCX без подтвержденного проекта изменений;
- не подтверждать спорные изменения без явного намерения пользователя.

Пример логики:

```text
Пользователь: «сформируй новую редакцию»
→ проверить наличие проекта изменений
→ если проекта нет: предложить сначала анализ
→ если проект есть, но есть спорные строки: показать спорные строки
→ если проект есть, но не подтвержден: попросить подтверждение проекта
→ если проект подтвержден: сформировать DOCX
→ запустить проверки
→ показать результат и ссылки
```

### 2. Исправить маршрутизацию подтверждений

Нужно добавить нормальные intent-сценарии:

- `confirm_safe_items` или использовать существующий `confirm_change_items`;
- `approve_change_project`;
- `reject_change_items`;
- `choose_source_priority` для конфликтов Excel/PDF.

Обновить `AgentIntentRouter`:

```ruby
return decision("approve_change_project", arguments, "0.9", "fallback") if normalized.match?(/подтверд.*проект|утверд.*проект|соглас.*проект/)
return decision("confirm_change_items", arguments, "0.9", "fallback") if normalized.match?(/подтверд.*строк|подтверд.*надежн|подтверд.*все.*спорн|соглас.*строк/)
```

Добавить eval-cases:

```ruby
Case.new(input: "подтверди проект изменений", expected_intent: "approve_change_project")
Case.new(input: "подтверди надежные строки", expected_intent: "confirm_change_items")
Case.new(input: "покажи строки, которые требуют подтверждения", expected_intent: "show_pending")
```

### 5. Исправить перенос финансирования в PDF-соглашениях

В `agreement_pdf_parser.py` есть `amount_mode == "transfer"`, но на уровне `ChangeSetBuilder` перенос сейчас не превращается в две корректные операции:

- уменьшить сумму в `from_year`;
- увеличить сумму в `to_year`.

Если PDF не дает источник бюджета или объект определен неуверенно — обе строки требуют подтверждения пользователя.

- «уменьшить на 10 000 000 руб.»;
- «увеличить на 10 000 000 руб.»;
- «исключить финансирование»;

### 6. Добавить полноценную самопроверку агента перед выдачей финального DOCX

Сейчас есть `PostExportDocxValidator`, это хорошо. Но нужен единый агрегированный сервис самопроверки:

```ruby
AgentSelfCheckService
```

Он должен проверять:

1. Суммы объектов складываются в мероприятия.
2. Мероприятия складываются в основные мероприятия.
3. Основные мероприятия складываются в подпрограммы.
4. Подпрограммы складываются в паспорт программы.
5. Паспорт DOCX после экспорта совпадает с целевой моделью.
6. Источники финансирования не потеряны.
7. Столбцы «Всего» пересчитаны.
8. DOCX повторно распарсился.
9. DOCX открылся через LibreOffice/render-check.
10. Нет неподтвержденных спорных строк.
11. Нет конфликтов Excel/PDF без решения пользователя.
12. Нет новых объектов с `manual_insert_required_count > 0`.

Результат самопроверки должен быть сохранен в `change_set.export_summary["agent_self_check"]`.

Финальный файл можно показывать в чате только если:

```ruby
change_set.export_ready? && agent_self_check.status == "passed"
```

Если проверка не прошла:

```text
Я сформировал черновик, но не выдаю его как финальный: паспортная сумма за 2028 год не совпадает с целевой моделью на 90 000 000 руб. Нужно проверить строку ...
```

### 7. Сделать ответы агента живыми, но строго основанными на инструментах

Сейчас `AgentResponseComposer` в основном шаблонный. Это безопасно, но не похоже на живого агента.

Добавить:

```ruby
AgentAnswerGenerator
```

Он должен использовать OpenRouter для финальной формулировки ответа, но только после выполнения инструментов.

Вход:

```json
{
  "user_message": "что поменялось по Черустям",
  "intent": "explain_change",
  "tool_result": {...},
  "workspace_context": {...},
  "knowledge_chunks": [...],
  "allowed_facts_only": true
}
```

Правила:

- LLM не считает деньги.
- LLM не придумывает строки, которых нет в `tool_result`.
- LLM не говорит «готово», если `tool_result.status` не финальный.
- LLM не показывает технические коды.
- LLM отвечает на русском, человеческим языком.
- Если данных не хватает — говорит, каких документов/подтверждений не хватает.
- Если LLM недоступна — fallback на текущий `AgentResponseComposer`.

Для надежности оставить текущие шаблонные ответы как `safe fallback`.

## Критерии приемки

Итерация считается готовой, если:

1. Пользователь может обычным языком пройти путь от анализа до готового DOCX.
2. Агент сам говорит, каких документов не хватает.
3. Агент показывает расхождения по годам/объектам с суммами и причиной.
4. Агент объясняет изменение по объекту/году/источнику.
5. Агент умеет подтверждать строки и проект через чат.
6. Агент не применяет изменения без подтверждения.
7. Агент учитывает все актуальные PDF-основания, а не только последний PDF.
8. Агент корректно обрабатывает перенос финансирования между годами.
9. Агент не выдает финальный DOCX, если самопроверка не прошла.
10. Готовые DOCX/отчет появляются карточками скачивания прямо в чате.
11. В пользовательском чате нет технических кодов и машинных терминов.
12. Rails tests и parser tests проходят.
13. Browser smoke: чат не дергается, автоскролл работает, кнопка отправки и плюс видны.
14. WORKLOG.md и README.md обновлены.
