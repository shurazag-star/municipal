- загрузку документов отдельно от чата;

> Пользователь загружает порядок, текущую DOCX-программу и документы-основания. Не переписывай проект с нуля. Исправь конкретные блокеры ниже.

## 1. Исправить OCR runtime в Docker/Rails/Sidekiq

### Проблема

Сейчас `ParserWorkerClient` запускает Python parser из Rails/Sidekiq-контейнера через `Open3.capture3`, используя путь вроде:

```ruby
PARSER_WORKER_PYTHON=/opt/parser-venv/bin/python
```

При этом `parser_worker/Dockerfile` содержит `tesseract`, но Rails/Sidekiq-контейнер, судя по `Dockerfile.rails`, устанавливает LibreOffice/poppler/python, но не устанавливает `tesseract-ocr`, `tesseract-ocr-rus`, `tesseract-ocr-eng`.

Значит, OCR fallback для сканированных PDF-соглашений может не работать именно там, где реально выполняется `ParseDocumentJob`.

### Нужно сделать

Выбери простой и надежный вариант для MVP:

1. Установить OCR-зависимости в `Dockerfile.rails`:

```bash
tesseract-ocr
tesseract-ocr-rus
tesseract-ocr-eng
```

2. Убедиться, что в контейнерах `web` и `sidekiq` доступны команды:

```bash
which tesseract
tesseract --list-langs
which pdftoppm
which pdfinfo
```

3. В тестовом/smoke-сценарии проверить наличие `rus` и `eng` именно в `sidekiq`:

```bash
docker-compose exec -T sidekiq bash -lc 'which tesseract && tesseract --list-langs | grep -E "rus|eng"'
```

4. Добавить это в README/WORKLOG.

### Приемка

Сканированный PDF без текстового слоя должен успешно разбираться через обычную загрузку в UI и `ParseDocumentJob`, а не только вручную внутри parser-worker контейнера.

## 2. Сделать workflow агента state-driven, а не только intent-driven

### Проблема

Сейчас агент в основном работает так:

```text
сообщение пользователя → intent → один-два tools → ответ
```

Для клиентского сценария агент должен учитывать состояние документов и сам вести пользователя по процессу.

### Нужно сделать

Добавить или усилить `AgentWorkflowPlanner` / `AgentWorkflowRunner`.

Логика должна быть такой:

#### Если пользователь просит “сформируй новую редакцию”, “подготовь DOCX”, “сделай файл”

1. Если нет загруженной DOCX-программы — агент отвечает: “Мне нужна текущая редакция муниципальной программы в DOCX. Загрузите ее в разделе документов или через плюс в чате”.
2. Если нет документов-оснований — агент отвечает: “Мне нужен отчет финансистов XLSX или PDF-основания изменений”.
3. Если нет анализа — агент сам запускает анализ и говорит: “Я подготовил проект изменений, перед формированием документа его нужно подтвердить”.
4. Если есть неподтвержденные/спорные строки — агент показывает их и просит подтверждение.
5. Если проект готов, но не утвержден пользователем — агент просит явное подтверждение проекта.
6. Если проект утвержден — агент формирует DOCX/отчет, запускает проверки, дает ссылки только при успешной проверке.

#### Если пользователь просит “проанализируй документы”

Агент должен:

1. проверить наличие нужных документов;
2. запустить анализ;
3. создать/обновить проект изменений;
4. кратко объяснить результат;
5. предложить следующие действия.

#### Если пользователь просит “проверь суммы”, “где расхождения”, “покажи несовпадения”

Агент должен:

1. показать контрольные итоги по годам;
2. показать строки/объекты, из-за которых возникли расхождения;
3. объяснить источник расхождений.

### Важно

Агент не должен автоматически утверждать проект изменений без явного пользовательского подтверждения.

## 3. Добавить подробный инструмент расхождений, а не только контрольные суммы по годам

### Проблема

`validate_control_sums` показывает в основном годовые итоги. Пользователь спрашивает живыми фразами:

- “где несовпадения?”
- “покажи расхождения”
- “почему не сходится 2028 год?”
- “что поменялось по Черустям?”
- “покажи строки, которые отличаются от Excel”

Ответ должен показывать не только год, сумму и дельту, но и конкретные строки/объекты.

### Нужно сделать

Добавить инструмент, например:

```ruby
show_discrepancies
```

или расширить `validate_control_sums`, но так, чтобы агент мог возвращать детальный список.

Минимальные поля для каждой строки расхождения:

- объект / мероприятие / подпрограмма;
- год;
- источник финансирования;
- сумма в текущей программе;
- сумма во внешнем источнике или предлагаемая новая сумма;
- разница;
- документ-основание;
- строка Excel или страница PDF, если есть;
- confidence сопоставления;
- причина: “сумма изменилась”, “объект найден во внешнем источнике, но отсутствует в программе”, “перенос между годами”, “конфликт Excel/PDF”, “требуется ручная проверка”.

### Приемка

Фразы должны работать через чат:

- “где несовпадения?”
- “покажи расхождения”
- “почему не сходится 2028 год?”
- “что по Черустям?”
- “какие строки требуют ручной проверки?”

Ответы должны быть человеческими и конкретными, без `ChangeSet`, `manual_insert_required`, `tool`, `parser`, `intent` и прочей технической лексики.

## 4. Исправить разрешение конфликтов между Excel и PDF

### Проблема

Сейчас `choose_source_priority` может записывать выбранный приоритет источника в `AnalysisSession.summary`, но это не обязательно меняет ChangeSet и не обязательно снимает блокировку self-check.

Если Excel и PDF дают разные суммы по одному объекту, пользователь должен выбрать источник, а система должна реально применить это решение.

### Нужно сделать

1. Конфликты должны храниться как разрешенные/неразрешенные.
2. Команда пользователя:

```text
используй Excel
```

или

```text
по этому объекту применяй PDF
```

должна:

- записать решение;
- исключить/отклонить конфликтующие изменения из другого источника;
- пересобрать проект изменений или обновить его строки;
- убрать конфликт из блокирующих проверок;
- оставить в отчете запись, что пользователь выбрал источник.

3. `AgentSelfCheckService` должен блокировать только неразрешенные конфликты.
4. `reusable_change_project` не должен повторно использовать старый проект, если изменилось решение по источнику.

### Приемка

Сценарий:

1. Загружены Excel и PDF, которые конфликтуют по одному объекту.
2. Агент говорит: “Есть конфликт: Excel показывает X, PDF показывает Y. Какой источник применить?”
3. Пользователь пишет: “используй Excel”.
4. Агент пересобирает/обновляет проект.
5. В финальный документ попадает Excel-значение.
6. Self-check не блокирует документ из-за уже разрешенного конфликта.

## 5. Сделать безопасное подтверждение строк

### Проблема

Если пользователь пишет “подтверди надежные строки”, система не должна подтверждать все строки подряд.

Опасные строки:

- низкая уверенность сопоставления;
- конфликт Excel/PDF;
- перенос финансирования между годами;
- OCR-распознавание с низкой уверенностью;
- неизвестный режим суммы;
- новый объект без надежного родителя/места вставки;
- строки, где нужна ручная вставка;
- строки с обнулением финансирования;
- строки, где сумма выглядит как дельта, но не абсолютная сумма.

### Нужно сделать

Разделить подтверждение на режимы:

#### `confirm_safe_items`

Для фраз:

- “подтверди надежные строки”
- “подтверди очевидные изменения”
- “подтверди безопасные”

Подтверждает только безопасные строки:

- confidence >= порога;
- нет конфликта;
- нет ручной вставки;
- не OCR low confidence;
- не unknown/transfer/zeroing без явного подтверждения;
- новый объект имеет надежное место вставки.

#### `confirm_specific_items`

Для фраз:

- “подтверди строки 12, 14, 19”
- “подтверди изменение по Черустям”

Подтверждает только выбранные строки.

#### `confirm_all_items`

Для фраз:

- “подтверди все”

Не должен сразу применять все. Агент должен сначала ответить:

> “Есть N спорных строк. Полное подтверждение может изменить программу по строкам с низкой уверенностью/конфликтами. Напишите: ‘подтверждаю все N строк’, если хотите продолжить”.

И только после точной фразы подтверждать все.

### Приемка

- “подтверди надежные строки” не подтверждает конфликтные/низкоуверенные строки.
- “подтверди все” без второй явной фразы не подтверждает опасные строки.
- В отчете видно, какие строки подтверждены автоматически как надежные, а какие подтверждены пользователем явно.

## 11. Усилить учет OCR и PDF-соглашений

### Нужно сделать

1. Если PDF разобран через OCR, сохранить это в parsed_data/source_reference.
2. Если OCR confidence низкий или текст фрагментарный — изменения требуют подтверждения.

   - “уменьшение”;
   - “перенос между годами”;
   - “обнуление”;
   - “не удалось надежно определить тип изменения”.

## 12. Обязательные сценарии приемки

### Сценарий 1. Новый клиент

1. Пользователь входит в пустой кабинет.
2. Агент говорит, что нужно загрузить:
   - порядок разработки/постановление;
   - текущую DOCX-программу;
   - Excel отчет финансистов или PDF-основания.
3. Никакой демо-программы не отображается как реальная.

### Сценарий 2. Анализ документов

1. Пользователь загрузил PDF-порядок, DOCX-программу, XLSX финансистов.
2. Пишет в чат: “проанализируй документы”.
3. Агент запускает анализ, создает проект изменений, сообщает:
   - сколько найдено изменений;
   - сколько надежных;
   - сколько требует подтверждения;
   - есть ли конфликты;
   - что делать дальше.

### Сценарий 3. Расхождения

Пользователь пишет:

```text
где несовпадения?
```

Агент показывает:

- итоги по годам;
- конкретные объекты/строки;
- источники данных;
- причины расхождений.

### Сценарий 4. Объектный вопрос

Пользователь пишет:

```text
что поменялось по Черустям?
```

Агент отвечает по объекту:

- где он найден;
- какие суммы изменились;
- по каким годам;
- из какого документа пришло основание;
- требуется ли подтверждение.

### Сценарий 5. Формирование без подтверждения

Пользователь пишет:

```text
сформируй новую редакцию
```

Если проект не утвержден, агент не формирует финальный DOCX, а говорит, что сначала нужно подтвердить проект/строки.

### Сценарий 6. Безопасное подтверждение

Пользователь пишет:

```text
подтверди надежные строки
```

Агент подтверждает только безопасные строки и сообщает, сколько осталось спорных.

### Сценарий 7. Финальный DOCX

После подтверждения проекта пользователь пишет:

```text
сформируй новую редакцию
```

Агент:

1. применяет проект;
2. пересчитывает суммы;
3. обновляет Word;
4. повторно парсит Word;
5. проверяет контрольные суммы;
6. проверяет открытие через LibreOffice;
7. если все хорошо — дает карточки скачивания DOCX и отчета;
8. если есть ошибка — не выдает документ как финальный, а объясняет проблему.

### Сценарий 8. Сканированный PDF

PDF без текстового слоя загружается через UI, разбирается в Sidekiq через OCR, агент создает изменения или просит подтверждение, если текст распознан ненадежно.

### Сценарий 9. Конфликт Excel/PDF

1. Excel и PDF дают разные суммы.
2. Агент видит конфликт.
3. Пользователь выбирает источник.
4. Система реально применяет выбранный источник.
5. Проверка не блокируется разрешенным конфликтом.

### Сценарий 10. Чистый чат

В пользовательском чате нет технических ролей, системных сообщений, debug-кодов и внутренней терминологии.
