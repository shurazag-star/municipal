## 1. Главный блокер: экспортированный DOCX не пересчитывает паспорт и агрегаты

### Что обнаружено

На реальном сценарии ChangeSet #38 был создан DOCX `changeset-38-version-3.docx`. Файл структурно открывается, вставленные строки есть, но контрольная арифметика в самом DOCX не доведена до конца.

Фактическая проверка повторным парсингом экспортированного DOCX показала:

- паспортные итоги исходного DOCX:
  - 2026: `2 296 101 960.00`
  - 2027: `1 866 791 200.00`
  - 2028: `690 689 180.00`
- паспортные итоги экспортированного DOCX — **остались такими же**, то есть не были обновлены;
- итоги XLSX-источника:
  - 2026: `2 253 220 255.91`
  - 2027: `1 776 791 196.12`
  - 2028: `780 689 180.00`

Также в таблицах мероприятий часть годовых ячеек обновилась, но ячейки `Всего` остались старыми. Пример: строка объекта/источника получила обновленную сумму по 2026 году, но общий столбец `Всего` не пересчитался.

### Требование

После применения ChangeSet экспортированный DOCX должен пройти повторную машинную проверку:

1. Паспортные итоги DOCX должны совпадать с целевой финансовой моделью.
2. Суммы по объектам должны складываться в мероприятия.
3. Мероприятия должны складываться в основные мероприятия.
4. Основные мероприятия должны складываться в подпрограммы.
5. Подпрограммы должны складываться в общий паспорт программы.
6. Горизонтальные итоги строк должны быть пересчитаны: `Всего = сумма по годам`, если в конкретной таблице такая логика применима.
7. Вертикальные итоги должны быть пересчитаны: агрегатная строка = сумма дочерних строк.
8. Если DOCX нельзя полностью исправить автоматически, агент должен явно показать блокирующий статус: `DOCX требует ручной доработки`, а не выдавать его как готовый.

### Что сделать в коде

#### 1.1. Добавить post-export validation

Создать сервис:

```ruby
PostExportDocxValidator
```

Вход:

- `program_version_id` целевой версии после ChangeSet;
- `generated_docx_attachment`;
- `analysis_session_id` или `source_document_id`, откуда взяты целевые суммы;
- допустимая денежная погрешность из `AgentSetting.money_tolerance`.

Сервис должен:

- повторно прогнать экспортированный DOCX через parser worker;
- сравнить паспортные итоги экспортированного DOCX с целевой моделью;
- сравнить агрегаты дерева;
- проверить горизонтальные итоги строк;
- сформировать `validation_result` с ошибками, предупреждениями и статусом:
  - `valid`
  - `valid_with_warnings`
  - `invalid`

Генерация файла не должна считаться завершенной, пока post-export validation не выполнена.

#### 1.2. Обновить `ChangeSetApplicationService`

После создания DOCX:

1. Запустить `PostExportDocxValidator`.
2. Записать результат в ChangeSet metadata.
3. Если статус `invalid`, в интерфейсе показывать красное предупреждение: документ сформирован, но контрольные суммы не сходятся, требуется исправление.
4. В отчете указать конкретные таблицы/строки/годы/источники, где ошибка.

## 2. Исправить парсинг координат DOCX

### Проблема

Сейчас parser worker хорошо извлекает дерево и годовые суммы, но недостаточно полно сохраняет координаты ячеек DOCX. Из-за этого patcher не знает, куда вставлять/обновлять:

- паспортные суммы;
- агрегатные строки `Итого`/`Всего`;
- столбцы `Всего`;
- некоторые родительские строки мероприятий/подпрограмм.

### Требование

Нужно хранить координаты всех финансовых ячеек, которые потенциально должны обновляться.

### Что сделать

В `docx_parser.py` расширить извлечение координат:

1. Для каждой финансовой таблицы определить:
   - индекс таблицы;
   - индекс строки;
   - индекс столбца источника финансирования;
   - индекс столбца `Всего`;
   - индексы годовых столбцов.
2. Для каждой строки таблицы сохранять координаты:
   - `total_cell_index`;
   - `year_cell_indexes`;
   - `source_cell_index`;
   - `row_type`: `object`, `event`, `main_event`, `subprogram`, `program_total`, `source_total`, `other`.
3. Для строк `Итого`/`Всего` не терять координаты. Даже если это агрегатная строка, она должна попадать в карту patch-плана.
4. Для паспортной таблицы создать отдельную карту координат по годам и источникам.

В Rails-модели можно добавить отдельную сущность или хранить в metadata:

```ruby
DocxCellCoordinate
# или metadata на ProgramNode/FundingLine
```

Рекомендуемая структура:

```json
{
  "table_index": 6,
  "row_index": 32,
  "source_cell_index": 2,
  "total_cell_index": 4,
  "year_cell_indexes": {
    "2026": 5,
    "2027": 6,
    "2028": 7,
    "2029": 8,
    "2030": 9
  },
  "row_type": "object",
  "node_id": 123,
  "budget_source": "local"
}
```

## 3. Исправить patch-план DOCX

### Проблема

Сейчас `DocxPatchClient` обновляет часть годовых ячеек и вставляет новые строки, но не гарантирует обновление всех затронутых агрегатов и паспортной таблицы.

### Требование

Перед patcher должен быть отдельный построитель плана:

```ruby
DocxPatchPlanBuilder
```

Он должен брать целевую версию программы после пересчета и формировать полный список ячеек для обновления.

### Что patch-план обязан обновлять

1. Все строки, напрямую измененные ChangeSet.
2. Все новые строки объектов.
3. Всех родителей измененных и новых объектов:
   - мероприятие;
   - основное мероприятие;
   - подпрограмма;
   - программа.
4. Все паспортные суммы.
5. Все ячейки `Всего` в измененных строках.
6. Все ячейки `Всего` в родительских агрегатах.
7. Все строки по источникам финансирования, если таблица ведет разрез по источникам.

### Важное правило

`new_object` влияет не только на вставку новой строки в DOCX. Он также должен добавлять своих родителей в список impacted nodes, чтобы patcher обновил все вышестоящие суммы.

## 4. PDF-соглашения/документы от министерства пока не реализованы

### Проблема

В UI есть тип `pdf_agreement`, но parser worker сейчас поддерживает только:

- `docx_program` → `parse-docx`;
- `xlsx_finance` → `parse-xlsx`;
- `pdf_procedure` → `parse-procedure-pdf`.

`pdf_agreement` не поддерживается и будет падать как неподдерживаемый тип документа. Это блокирует один из ключевых бизнес-сценариев: пользователь загружает соглашение/письмо/документ от министерства, а агент находит изменения по объектам.

### Требование

Реализовать полноценный поток для `pdf_agreement`.

### Что сделать

#### 4.1. ParserWorkerClient

Добавить:

```ruby
"pdf_agreement" => "parse-agreement-pdf"
```

#### 4.2. CLI parser worker

Добавить команду:

```bash
parse-agreement-pdf path/to/file.pdf
```

#### 4.3. Формат результата

Parser должен возвращать JSON:

```json
{
  "document_type": "pdf_agreement",
  "changes": [
    {
      "object_name": "...",
      "event_name": "...",
      "year": 2026,
      "budget_source": "regional|local|federal|other|unknown",
      "old_amount": null,
      "new_amount": "123456.78",
      "delta_amount": null,
      "evidence_text": "фрагмент документа",
      "page": 5,
      "confidence": 0.82
    }
  ],
  "warnings": []
}
```

#### 4.4. Использование LLM

LLM можно использовать только для извлечения структурированных изменений из сложного текста PDF, но не для финальной арифметики.

Схема:

1. deterministic PDF text extraction;
2. chunking;
3. OpenRouter extraction по строгой JSON Schema;
4. schema validation;
5. нормализация сумм через Decimal/BigDecimal;
6. matching к дереву программы;
7. ChangeSet.

## 5. Чат-агент пока является маршрутизатором, а не полноценным агентом

### Проблема

Текущий `AgentOrchestrator` определяет действия по ключевым словам и вызывает Rails-сервисы. Это полезный MVP, но это еще не полноценный чат-агент.

Ограничения:

- системная инструкция агента из `AgentSetting` фактически не управляет поведением обычного чата;
- база знаний из PDF-порядка не используется для обычных ответов;
- агент плохо понимает свободные формулировки вроде:
  - «выгрузи новую редакцию»;
  - «подготовь отчет»;
  - «что поменялось по Черустям»;
  - «почему сумма 2028 стала больше»;
  - «покажи, какие строки требуют ручной вставки»;
- OpenRouter-модель используется не как planner/tool-calling agent, а точечно.

### Требование

Сделать агентскую схему:

```text
User message
  → LLM Planner / Intent Classifier
  → Tool Registry
  → deterministic tools
  → Result Formatter
  → Chat response with links/actions
```

### Инструменты агента

Зарегистрировать реальные tools:

- `get_workspace_context`
- `search_knowledge_base`
- `parse_uploaded_documents`
- `build_program_tree`
- `analyze_finance_source`
- `create_changeset`
- `show_changeset`
- `confirm_changeset_rows`
- `apply_changeset`
- `generate_docx`
- `validate_generated_docx`
- `generate_report`
- `explain_change`
- `list_generated_documents`

LLM выбирает инструмент, но деньги считает только deterministic code.

### Минимальный безопасный вариант

Если полноценный tool-calling через OpenRouter делать долго, сначала добавить LLM intent classifier:

```json
{
  "intent": "generate_docx|create_changeset|explain_change|show_pending|validate|smalltalk|unknown",
  "arguments": {
    "object_query": "Черустях",
    "change_set_id": 38
  },
  "confidence": 0.91
}
```

Дальше Rails вызывает только разрешенные сервисы.

## 6. UX: клиентский сценарий должен быть проще

### Требуемый сценарий

1. Пользователь заходит в кабинет.
2. Система показывает 3 понятных шага:
   - `1. Загрузите порядок разработки`
   - `2. Загрузите текущую муниципальную программу`
   - `3. Загрузите документ-основание изменений: XLSX финансистов или PDF соглашения`
3. Агент в чате пишет, что готово и что он видит.
4. Пользователь нажимает/пишет: `Проанализируй изменения`.
5. Агент показывает проект изменений:
   - что найдено;
   - что совпало точно;
   - что спорно;
   - что требует ручной проверки;
   - какие суммы изменятся.
6. Пользователь подтверждает ChangeSet.
7. Агент применяет изменения, пересчитывает, формирует DOCX и отчет.
8. Агент запускает post-export validation.
9. Если все сошлось — показывает:
   - `Готово. Новая редакция муниципальной программы сформирована.`
   - кнопки `Скачать DOCX`, `Скачать отчет`, `Посмотреть изменения`.
10. Если не сошлось — показывает не «готово», а список блокирующих проблем.

### Что поправить сейчас

1. На странице `/documents` показывать сформированные файлы, а не пустой массив `@generated_documents = []`.
2. Добавить bulk-action:
   - `Подтвердить все надежно сопоставленные строки`;
   - `Подтвердить все новые объекты с уверенностью выше порога`;
   - но опасные/непонятные строки оставлять на ручную проверку.
3. Убрать из пользовательского интерфейса технические статусы, если они не объяснены человеческим языком.
4. Для `MANUAL_INSERT_REQUIRED` показывать конкретное место, куда пользователь должен вставить строку, и почему авто-вставка невозможна.

## 7. Отчет должен быть управленческим, а не только техническим

HTML-отчет уже есть, но нужен отчет, который удобно отдавать руководителю/финансистам.

Добавить в отчет:

1. Краткое резюме:
   - сколько строк изменено;
   - сколько объектов добавлено;
   - сколько сумм пересчитано;
   - сколько строк требует ручной проверки;
   - прошла ли контрольная сверка.
2. Таблица изменений:
   - подпрограмма;
   - основное мероприятие;
   - мероприятие;
   - объект;
   - год;
   - источник;
   - старая сумма;
   - новая сумма;
   - разница;
   - основание;
   - статус.
3. Раздел контрольных сумм:
   - до;
   - после;
   - источник изменений;
   - отклонение.
4. Раздел предупреждений.
5. Ссылки на созданные файлы.

Желательно добавить экспорт отчета в XLSX или DOCX, но для ближайшей итерации достаточно улучшенного HTML + downloadable attachment.

## 8. Delivery hygiene перед передачей заказчику

В архиве/репозитории не должно быть:

- `.env` с реальными или пустыми локальными настройками, кроме `.env.example`;
- `docker-compose.override.yml` с абсолютным локальным путем пользователя;
- `storage/` с тестовыми/generated файлами;
- `log/`;
- `.pytest_cache/`;
- `__pycache__/`;
- `.playwright-mcp/`;
- временных отчетов и локальных прогонов.

`docker-compose.override.yml` должен быть либо не включен, либо заменен на `docker-compose.override.example.yml`.
