# CODEX TASK 04 — финализация клиентского сценария и живого агента

## Цель

Довести приложение `Municipal` до клиентского сценария:

> Пользователь заходит в личный кабинет, один раз загружает порядок разработки муниципальной программы, загружает текущую редакцию муниципальной программы, затем загружает документы-основания изменений — XLSX финансистов и/или PDF-соглашения/письма. Далее он общается с агентом в чате обычным языком. Агент анализирует документы, показывает понятный проект изменений, просит подтвердить спорные изменения, пересчитывает программу инструментами, формирует новую редакцию DOCX и отчет, проверяет контрольные суммы и отдает пользователю готовые файлы.

Важно: чат должен быть живым пользовательским интерфейсом, а не debug-панелью и не набором машинных статусов.

## Нельзя в пользовательском чате

В ответах агента пользователю нельзя показывать внутренние термины:

- `parser worker`
- `post_export_validation`
- `deterministic`
- `PROGRAM_TOTAL_DIFF`
- `ChangeSet` без перевода на русский пользовательский смысл
- `LlmRun`
- `intent`
- `tool_call`
- `metadata`
- `manual_insert_required` как машинный статус
- `INSERTED_IN_DOCX` как машинный статус
- любые JSON/debug payloads

Допустимые пользовательские формулировки:

- `проект изменений`
- `проверка контрольных сумм`
- `новая редакция Word-документа`
- `отчет об изменениях`
- `строки, которые требуют ручного подтверждения`
- `строки, которые я вставил автоматически`
- `документ прошел проверку`
- `документ не готов: есть расхождения`

## Итерация 2. Сделать чат живым, а не шаблонным роутером

### Текущая проблема

Сейчас агент в основном работает как intent-router:

`сообщение пользователя → классификация намерения → шаблонный ответ`

Это безопасно, но не ощущается как полноценный агент. Пользователь должен иметь возможность писать обычным языком:

- `проанализируй документы`
- `что изменилось по Черустям?`
- `почему 2028 стал больше?`
- `покажи спорные строки`
- `подтверди надежные изменения`
- `сформируй новую редакцию`
- `дай отчет`
- `проверь еще раз контрольные суммы`
- `где взять готовый файл?`

И агент должен отвечать по-человечески, вести процесс и вызывать инструменты.

### Требование

Ввести нормальную агентскую схему:

```text
User message
→ AgentOrchestrator
→ AgentContextBuilder
→ AgentIntentRouter / LLM planner
→ AgentToolRegistry
→ выполнение инструментов
→ AgentResponseComposer
→ assistant message с понятным ответом и ссылками/кнопками
```

### AgentToolRegistry

Создать Rails-сервис `AgentToolRegistry` с реальными инструментами, а не заглушками.

Минимальный набор инструментов:

1. `get_workspace_context`
   - какие документы загружены;
   - какие документы распарсены;
   - какая программа активна;
   - есть ли текущий проект изменений;
   - есть ли готовые файлы.

2. `search_knowledge_base(query)`
   - ищет по PDF-порядку разработки;
   - возвращает понятные выдержки/пересказ;
   - по возможности возвращает страницу/источник.

3. `run_analysis`
   - анализирует текущую программу и документы-основания;
   - создает или переиспользует проект изменений.

4. `get_or_create_change_project`
   - если уже есть актуальный pending-проект по тем же документам, не плодит новый;
   - если документы изменились — создает новый.

5. `show_change_project`
   - показывает краткую сводку проекта изменений.

6. `show_pending_items`
   - показывает строки, которые требуют подтверждения.

7. `confirm_change_items`
   - подтверждает конкретные строки или все безопасные строки;
   - опасные массовые подтверждения требуют явного подтверждения пользователя.

8. `approve_change_project`
   - переводит проект изменений в состояние, когда его можно применить.

9. `apply_change_project`
   - применяет подтвержденный проект изменений;
   - формирует DOCX и отчет;
   - запускает повторный парсинг, контроль сумм и render-проверку.

10. `validate_control_sums`
    - проверяет суммы по дереву программы.

11. `validate_exported_docx`
    - проверяет именно сформированный DOCX.

12. `list_generated_documents`
    - показывает готовые DOCX/отчеты.

13. `get_download_links`
    - возвращает ссылки для скачивания готовых файлов.

14. `explain_change`
    - объясняет конкретное изменение: объект, год, источник, старая сумма, новая сумма, основание.

15. `compare_sources`
    - сравнивает данные XLSX и PDF-соглашений, если загружены оба типа.

### AgentResponseComposer

Добавить сервис `AgentResponseComposer`, который формирует человеческий ответ после выполнения инструментов.

Можно использовать LLM для финальной формулировки, но с жестким правилом:

- модель не считает деньги;
- модель не придумывает суммы;
- модель получает только результаты инструментов;
- все числа в ответе берутся из tool result;
- если tool result говорит `not_ready`, агент не пишет `готово`.

Если LLM недоступна, использовать безопасные русские шаблоны без технических слов.

## Итерация 5. Не показывать невалидный DOCX как готовый

### Проблема

Если post-export validation возвращает `invalid`, система не должна считать документ готовым и не должна показывать его пользователю как финальный файл.

### Требование

1. `ChangeSetApplicationService#apply!`:
   - если проверка экспорта не прошла, НЕ переводить проект в финальный успешный статус;
   - НЕ писать пользователю `готово`;
   - НЕ показывать DOCX как готовый файл.

2. Допустимо хранить диагностический черновик, но явно помечать его:
   - `черновик для диагностики`
   - доступен только admin/debug или отдельной кнопкой `скачать черновик`, если это нужно.

3. Добавить статусы:
   - `export_ready` / `applied` — только если все проверки прошли;
   - `export_failed` — если DOCX создан, но проверки не прошли;
   - `needs_manual_review` — если остались строки для ручной проверки.

4. В пользовательском чате:
   - если экспорт не прошел, агент объясняет проблему и предлагает исправить;
   - финальную ссылку на DOCX не показывает.

5. Тест:
   - искусственно сломать сумму в DOCX patch result;
   - убедиться, что пользователь не получает финальную кнопку скачивания готового DOCX.

## Итерация 6. Усилить post-export validation

### Сейчас хорошо

Уже есть повторный парсинг DOCX и render-проверка через LibreOffice.

### Нужно усилить

Проверять не только паспортные итоги, но всю финансовую структуру:

1. По каждой строке финансирования:
   - суммы по годам;
   - столбец `Всего`, если он есть;
   - источник финансирования.

2. По каждому объекту:
   - сумма объекта = сумма его строк финансирования.

3. По каждому мероприятию:
   - сумма мероприятия = сумма объектов.

4. По каждому основному мероприятию:
   - сумма основного мероприятия = сумма мероприятий.

5. По каждой подпрограмме:
   - сумма подпрограммы = сумма основных мероприятий.

6. По программе:
   - сумма программы = сумма подпрограмм.

7. По паспорту:
   - паспортные суммы = итоговая сумма программы.

8. По источникам:
   - источники в паспорте = сумма источников по дереву.

Если какая-то координата не найдена, агент должен не молчать, а пометить:

```text
нужно проверить вручную: не удалось найти ячейку для обновления...
```

## Итерация 9. PDF-соглашения: абсолютная сумма или дельта

### Проблема

PDF-соглашение может содержать разные формулировки:

- `предусмотреть 10 000 000 руб.` — абсолютное значение;
- `увеличить на 10 000 000 руб.` — дельта;
- `уменьшить на 10 000 000 руб.` — дельта;
- `перенести с 2026 на 2027` — перенос;
- `исключить финансирование` — обнуление/снятие лимитов.

Нельзя всегда считать последнюю сумму новой абсолютной суммой.

### Требование

В `parse_pdf_agreement` добавить поле:

- `amount_mode`: `absolute`, `delta_plus`, `delta_minus`, `transfer`, `zeroing`, `unknown`
- `old_amount_rub`
- `new_amount_rub`
- `delta_rub`
- `from_year`
- `to_year`
- `confidence`
- `evidence_text`
- `page`

Если режим `unknown` или уверенность низкая — строка должна идти в ручное подтверждение.

Допустимо использовать LLM extraction через OpenRouter с JSON schema, но только для извлечения структуры и объяснения. Расчеты все равно выполняет код.

## Итерация 10. Конфликты между XLSX и PDF

### Проблема

Если загружены XLSX финансистов и PDF-соглашение, они могут давать разные суммы по одному объекту/году/источнику.

### Требование

Добавить сервис `SourceConflictDetector`:

- группирует изменения по объекту, году, источнику;
- сравнивает значения из XLSX и PDF;
- если разные значения — создает конфликтный пункт;
- агент спрашивает пользователя, какой источник считать приоритетным.

Пример ответа:

```text
Я нашел расхождение между Excel финансистов и PDF-соглашением по объекту «...», 2027 год.

Excel: 12 000 000 руб.
PDF: 15 000 000 руб.

Какой источник применить?
[Использовать Excel]
[Использовать PDF]
[Оставить на ручную проверку]
```

## Критерии приемки финала

Считать этап завершенным только если выполнено всё ниже:

1. Пользователь может пройти полный сценарий через чат без перехода в debug-разделы.
2. В чате не отображаются системные/tool-сообщения.
3. В чате нет машинных статусов и внутренних терминов.
4. Агент использует инструменты для анализа, пересчета, проверки и формирования файлов.
5. LLM не считает деньги напрямую и не придумывает суммы.
6. PDF-порядок используется как база знаний.
7. XLSX и PDF-основания изменений поддерживаются.
8. Конфликты между источниками выявляются и требуют решения пользователя.
9. DOCX формируется только после подтвержденного проекта изменений.
10. Невалидный DOCX не показывается как готовый.
11. Валидный DOCX проходит:
    - повторный парсинг;
    - проверку дерева сумм;
    - проверку паспортных итогов;
    - проверку источников;
    - проверку `Всего`;
    - LibreOffice render.
12. В чате появляются кнопки скачивания новой редакции DOCX и отчета.
13. `/documents` показывает готовые документы.
14. Модель, выбранная в настройках OpenRouter, реально используется агентом.
15. В коде нет жесткой привязки к одному муниципалитету.
16. Все тесты проходят.
