# Муниципальный программный агент

Проект по `TZ_AI_agent_municipal_programs.md`, `CODEX_TASK_02_CHAT_AGENT_REFACTOR.md`, `CODEX_TASK_03_READY_EXPORT_AND_AGENT_FIXES.md`, `CODEX_TASK_04_FINAL_PRODUCT_AGENT.md`, `CODEX_TASK_05_FINAL_AGENT_ORCHESTRATION.md`, `CODEX_TASK_06_FINAL_HARDENING.md`, `CODEX_TASK_07_AUTONOMOUS_AGENT_FINALIZATION.md` и `CODEX_TASK_11_SEMANTIC_AGENT_MATCHING_UNIVERSALITY.md`.

Текущий продуктовый сценарий: пользователь работает через чат муниципального агента. Агент видит загруженные документы, автономно сопоставляет изменения, пересчитывает дерево программы, формирует новую редакцию DOCX и отчет только после успешной проверки. Пользователь не подтверждает каждую строку вручную; если часть строк нельзя надежно применить по документам, агент объясняет причину и не применяет их молча.

## Что уже проверяется

- Все денежные значения хранятся в рублях через `Decimal`.
- DOCX-значения в тыс. руб. конвертируются в рубли.
- Источники финансирования нормализуются в справочник.
- Excel-строки классифицируются до суммирования.
- Дубли объектов группируются по мероприятию, коду объекта и нормализованному имени.
- Строка `0000000000.0000000000` сохраняется как служебная нераспределенная строка Excel.
- Итоговая строка `Итого:` не суммируется второй раз.
- Паспортная сверка DOCX/Excel выявляет расхождения без показа сырых технических статусов в основном UI.
- AnalysisSession сопоставляет разобранные XLSX/PDF-источники с деревом программы и создает проект изменений.
- `pdf_agreement` проходит через команду разбора `parse-agreement-pdf` и сохраняет изменения с page/evidence.
- Проект изменений показывает объект, год, источник, старую/новую сумму, разницу, основание и решение агента без ручных кнопок подтверждения строк.
- Root page открывает рабочее место агента: чат, context panel и быстрые действия.
- Настройки агента хранят system prompt, модель, температуру, пороги сопоставления и флаги политики.
- `AgentWorkflowRunner` выполняет цепочку действий агента за одно сообщение или через фоновую задачу: анализ, сверка, автономное сопоставление, формирование и проверка.
- `AgentToolRegistry` выполняет действия агента, а `AgentResponseComposer`/`AgentAnswerGenerator` формируют человекочитаемые ответы и карточки скачивания.
- Анализ использует явный режим источника: `xlsx_target`, `pdf_patch`, `xlsx_target_with_pdf_evidence` или `auto`. В режиме Excel + PDF Excel остается целевой моделью, а PDF используется как подтверждение/конфликт, без автоматического добавления поверх Excel.
- PDF-перенос финансирования раскладывается на две строки: уменьшение старого года и увеличение нового года; агент применяет их только после автономной проверки.
- Для сложных совпадений `SemanticMatchAgent` получает короткий пакет строки и 5-10 кандидатов DOCX, выбирает смысловое сопоставление строго по JSON-схеме и сохраняет решение в `agent_match_decisions`.
- `IndependentVerifierAgent` и расчетные валидаторы проверяют решения semantic layer; деньги, rollup, паспортные итоги и DOCX-сверку считает только код.
- В режиме `pdf_patch` формируется PDF patch ledger: было -> операция -> должно стать. После экспорта DOCX операции проверяются по расчетному дереву и повторной DOCX-проверке.
- Чат поддерживает точечные команды по объекту: `проверь объект ...`, `пересчитай ...`, `почему по нему изменилась сумма`, `перепроверь эту строку`; память чата хранит последний объект и режим источника.
- Профиль муниципального документа сохраняет роль документа, паспорт, расчетные таблицы, годы, колонку `Всего`, единицы денег и источники бюджета, чтобы parser не зависел молча от одной структуры таблиц.
- Вопросы `где несовпадения?`, `покажи расхождения`, `почему не сходится 2028 год?` показывают конкретные объекты, годы, источники, разницы и документ-основание.
- Фразы старого ручного сценария вроде `подтверди надежные строки` и `подтверди проект` переводятся в автономную подготовку новой редакции, а не в ручное подтверждение строк.
- Выбор `используй Excel` или `используй PDF` перестраивает текущий проект изменений: конфликтующие строки другого источника отклоняются, а блокировка проверки снимается.
- Агент использует историю чата для уточняющих вопросов вроде `а почему по нему сумма изменилась?`.
- `AgentSelfCheckService` блокирует выдачу финального DOCX, если остались неразобранные агентом строки, конфликты Excel/PDF, ручные вставки или не пройдена проверка документа.
- Старые и новые сообщения агента очищаются от внутренних терминов перед показом пользователю.
- Финальные DOCX/отчет доступны в чате и на странице документов только если сформированный Word-документ прошел проверку.

## TASK 12: ручной ввод, approval lifecycle и E2E

После `CODEX_TASK_12_MANUAL_INPUT_APPROVAL_E2E.md` агент поддерживает три рабочих источника изменений:

- `xlsx_target`: Excel финансистов является целевой финансовой моделью.
- `pdf_patch`: PDF-основание является частичным набором операций, которые проверяются через PDF patch ledger.
- `manual_instruction`: текстовая команда пользователя в чате становится формальным основанием изменения.

Также доступны `auto` и `xlsx_target_with_pdf_evidence`. В режиме Excel + PDF Excel остается главным источником сумм, а PDF используется как подтверждение или источник конфликта, без двойного учета.

Ручной ввод работает через безопасную цепочку: извлечение структурированной инструкции, проверка обязательных полей, поиск объекта, уточняющий вопрос при неоднозначности, детерминированный пересчет, генерация DOCX, post-export проверка и только затем карточки скачивания. Если пользователь пишет `утверждено`, `сделай актуальной` или аналогичную фразу, последняя проверенная сгенерированная версия становится активной. Если есть активная версия и неутвержденный черновик, агент спрашивает, куда вносить следующую правку.

Итоговая live-проверка TASK 12 выполнена на новой тестовой организации:

- A-C: Excel target model, повторный Excel после утверждения, zero/new-object сценарий.
- D-F: PDF absolute, PDF transfer, ambiguous PDF object с уточнением.
- G-I: полный ручной запрос, ручной запрос с уточнением источника, выбор активная/черновик.

Результаты зафиксированы в `E2E_AGENT_VALIDATION_REPORT.md`. Для A-I использовался быстрый post-export validator внутри `rails runner`, чтобы не повторять тяжелый DOCX reparse/render девять раз в одном процессе; реальный `parser_worker` и Rails post-export логика покрыты автоматическими тестами и отдельными прогонами.

## Docker/Rails запуск

Локальный запуск:

```bash
cp .env.example .env
colima start --cpu 2 --memory 4 --disk 20
docker-compose up -d --build
```

После запуска Rails доступен на:

```text
http://localhost:3000
```

В текущем окружении стек уже был поднят и проверен через `docker-compose ps`, `curl` и браузерную проверку.

OCR и визуальные проверки должны быть доступны именно в Rails/Sidekiq-образе, потому что обычный разбор документов запускается из Rails/Sidekiq:

```bash
docker-compose exec -T sidekiq bash -lc 'which tesseract && tesseract --list-langs | grep -E "rus|eng"'
docker-compose exec -T sidekiq bash -lc 'which pdftoppm && which pdfinfo && which soffice'
```

Рабочий вход:

```text
email: admin@example.com
password: password123
```

Практический поток:

1. Открыть `http://localhost:3000`.
2. Войти под seed-пользователем.
3. На главном экране работать в чате агента и смотреть `Контекст агента`.
4. Открыть `Документы` и загрузить порядок разработки, текущую DOCX-программу и документы-основания.
5. Открыть `Настройка агента`, выбрать модель OpenRouter и политику работы агента.
6. Вернуться в `Рабочее место` и писать агенту обычным языком: `проанализируй документы`, `где несовпадения?`, `что поменялось по Черустям?`, `пересчитай программу`, `сформируй новую редакцию`.
7. Когда агент покажет карточки скачивания, DOCX и отчет уже прошли расчетные проверки. Если проверка не пройдена, агент покажет причину и не выдаст файл как финальный.

Агент запускает анализ, создает проект изменений, объясняет изменения, показывает строки, которые не удалось надежно разобрать, и формирует DOCX/отчет через расчетные Rails-сервисы после автономной проверки.

## Муниципальные tenant-профили

Один Rails/Railway деплой обслуживает несколько муниципалитетов через разные `Organization`.
Документы, чат, версии программы, проекты изменений, настройки агента и пользователи привязаны к организации.

Текущий рабочий tenant Люберец можно пометить без переноса документов, указав id существующей организации:

```bash
LYUBERTSY_ORGANIZATION_ID=<id> \
LYUBERTSY_ADMIN_EMAIL=<admin-email> \
LYUBERTSY_EMPLOYEE_EMAIL=<employee-email> \
bin/rails municipal:provision_lyubertsy
```

Шатура создается отдельной организацией и клонирует базовые настройки агента с Люберец, но дальше редактируется независимо:

```bash
PROVISION_SHATURA=true \
SHATURA_ADMIN_EMAIL=<admin-email> \
SHATURA_ADMIN_PASSWORD=<secret> \
SHATURA_EMPLOYEE_EMAIL=<employee-email> \
SHATURA_EMPLOYEE_PASSWORD=<secret> \
bin/rails municipal:provision_shatura
```

В production реальные пароли задаются только через переменные окружения. Загруженные документы Люберец и Шатуры не смешиваются, потому что все выборки идут через `current_organization`.

## OpenRouter

Ключ не хранится в репозитории. Для подключения LLM заполните локальный `.env` или внешний env-файл в `~/.codex/secrets`:

```bash
OPENROUTER_API_KEY=sk-or-v1-...
OPENROUTER_MODEL_PRIMARY=deepseek/deepseek-v4-pro
OPENROUTER_MODEL_FAST=deepseek/deepseek-v4-flash
OPENROUTER_SITE_URL=http://localhost:3000
OPENROUTER_APP_NAME=Municipal Program Agent
```

В кабинете администратора откройте `/admin/openrouter_settings`, нажмите `Загрузить модели`, затем выберите нужную модель. По умолчанию используется `DeepSeek: DeepSeek V4 Pro` (`deepseek/deepseek-v4-pro`).

Python gateway использует официальный endpoint:

```text
https://openrouter.ai/api/v1/chat/completions
```

Денежные суммы, контрольные итоги и пересчет дерева делает только код Rails/Python через точную денежную арифметику. LLM допускается для выбора действия, объяснений, классификации спорных случаев и подготовки текста, но не для арифметики.

## Ручная генерация отчета

```bash
./.venv/bin/python parser_worker/cli.py generate-report \
  --docx 'sample_documents/проект изменений МП_март_2026 (10).docx' \
  --xlsx 'sample_documents/Отчет_о_финансировании_мероприятий_целевых_программ+_Расширенный.xlsx' \
  --pdf 'sample_documents/2. № 2291 от 16.10.2025.pdf' \
  --out storage/outputs
```

Для ручной проверки gateway можно запросить LLM-объяснение расхождений:

```bash
set -a
. ./.env
set +a
./.venv/bin/python parser_worker/cli.py explain-report \
  --mapping-report storage/outputs/mapping_report.json \
  --model deepseek/deepseek-v4-pro \
  --out storage/outputs/openrouter_explanation.json
```

После изменения env перезапустите web/sidekiq:

```bash
docker-compose restart web sidekiq
```

## Архитектура

```text
rails_app/        Rails app: рабочее место агента, чат, настройки, документы, admin/settings
```

## Текущий статус

- Rails UI запускается, требует вход, принимает загрузку файлов, вызывает модуль разбора документов, сохраняет `parsed_payload`, показывает чат-рабочее место и context panel.
- Полное дерево DOCX сохраняется в `ProgramNode`/`FundingLine`; AnalysisSession создает проект изменений из XLSX и PDF agreement payload.
- Ручное подтверждение спорных строк скрыто из основного сценария; применимость строк решает автономный резолвер агента.
- Применение и формирование DOCX реализованы через проект изменений, автономное сопоставление, patch plan, повторный парсинг DOCX и LibreOffice render validation.
- OpenRouter live-запрос требует пользовательский ключ; модели загружаются в кабинете администратора.
- PDF agreement parser использует текстовый слой PDF, а при его отсутствии запускает OCR через `pdftoppm` + `tesseract` с русским и английским языками.
- PDF agreement parser различает абсолютную сумму, увеличение, уменьшение, перенос, обнуление и неясные случаи; неясные строки уходят в уточнение и не применяются молча.
- Чат-агент использует LLM intent classifier и LLM answer generator при наличии OpenRouter, а также безопасный fallback; деньги считает только код, опасные/неясные команды переводятся в отказ или точечное уточнение.
- Агент распознает живые команды про расхождения, пересчет, новую редакцию, готовые файлы и выбор приоритета Excel/PDF.
- Конфликты между Excel и PDF выявляются и не применяются автоматически.
- В Docker-образах установлены `libreoffice-writer`, `poppler-utils`, `tesseract-ocr`, `tesseract-ocr-rus`, `tesseract-ocr-eng`; smoke-проверка реального DOCX через LibreOffice возвращает `valid`.
